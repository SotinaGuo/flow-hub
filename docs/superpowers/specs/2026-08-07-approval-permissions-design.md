# 审批权限设计

## 目标

为申请详情页增加基于角色的审批权限控制，确保只有具备 `approver` 或 `admin` 角色的用户可以执行审批操作，普通申请人只能查看申请详情。

## 范围

- 增加 Mock 当前用户会话和角色模型。
- 增加统一的审批权限判断函数。
- 在申请详情页按权限显示或隐藏审批操作。
- 在申请仓储层再次校验审批权限，避免绕过界面直接调用状态更新。
- 覆盖有权限和无权限用户的单元测试。

本阶段不实现登录、用户管理、角色配置后台、部门审批流配置或持久化权限数据。

## 角色模型

代码中的角色使用英文枚举值，界面文案使用中文：

| Role        | 权限                 |
| ----------- | -------------------- |
| `applicant` | 查看申请，无审批权限 |
| `approver`  | 审批待处理申请       |
| `admin`     | 审批待处理申请       |

Mock 当前用户默认为 `approver`，以保持现有审批演示流程可用。测试使用 `applicant` 验证拒绝路径，使用 `approver` 和 `admin` 验证允许路径。

## 架构

### 用户与权限

在 `src/lib/auth/` 下建立以下边界：

- `types.ts`：定义 `UserRole` 和 `User`。
- `session.ts`：提供 Mock 当前用户 `currentUser`。
- `permissions.ts`：提供 `canApprove(user)`，集中维护角色到审批能力的映射。

审批权限只依赖用户角色，不依赖申请人的部门或职位。后续扩展部门审批流时，只需替换权限策略，不修改详情页的按钮渲染逻辑。

### 状态更新数据流

申请详情页调用仓储层更新状态时传入当前用户：

```text
Detail Page -> applicationRepository.updateStatus(id, status, currentUser)
                         |
                         v
                    canApprove(user)
                         |
              allowed -> update status
              denied  -> throw permission error
```

仓储层是最终权限边界。页面层的按钮隐藏只负责用户体验，不能替代仓储层校验。

## 页面行为

- 当前申请状态为 `pending` 且用户角色为 `approver` 或 `admin`：显示“通过申请”“驳回申请”“撤回申请”。
- 当前申请状态为 `pending` 且用户角色为 `applicant`：不显示审批按钮，显示“当前用户没有审批权限”。
- 申请不是 `pending`：保持现有流程记录展示，不显示处理操作。
- 发生权限拒绝或状态更新失败：使用现有 `alert` 反馈区域显示错误信息。

## 错误处理

仓储层在无审批权限时抛出稳定的英文错误标识或可识别错误信息，详情页将其转换为中文提示。权限拒绝不修改申请状态、不追加流程记录。

## 测试策略

- `src/lib/auth/permissions.test.ts`
  - `applicant` 无审批权限。
  - `approver` 有审批权限。
  - `admin` 有审批权限。
- `src/lib/application/repository.test.ts`
  - 无权限用户更新状态失败。
  - 有权限用户可以更新状态。
  - 权限拒绝不会改变申请状态或历史记录。
- 申请详情页测试
  - 无权限用户看到权限提示且看不到审批按钮。
  - 有权限用户可以看到审批按钮。

## 验收标准

1. 申请人角色访问待审批详情时不能看到或执行审批操作。
2. 审批人和管理员角色可以执行现有审批状态流转。
3. 直接绕过页面调用仓储层也不能绕过权限校验。
4. 现有状态流转、申请提交和列表展示功能保持不变。
